# Backend/database integration outcomes

## Brand and frontend preservation
- [ ] Keep the approved visual design, layout, typography, colors, spacing, responsive behavior, assets and current page interactions intact; make only the minimum frontend changes needed to connect APIs. Use “Khanfem” consistently and remove leftover prior-brand references without changing the visual identity. Preserve stable product IDs, category mapping, image paths, product URLs, cart payloads and history-compatible storage behavior.
- [ ] Keep working single-page navigation, categories and filters, combined Drinks display, full-menu current-category behavior, carousel, cart, product detail, checkout, confirmation, tracking, review and reservation flows. Do not rebuild existing working UI unnecessarily.

## PostgreSQL schema and reproducibility
- [ ] Use a normalized relational PostgreSQL schema with appropriate primary/foreign keys, one-to-many and order/product many-to-many through order items, unique/check/not-null constraints, safe deletion/update rules, indexes, transactions and referential integrity. Include users/roles, categories, products, orders, order items and option/price snapshots, payments, reservations, reviews, notifications, status history, configurable hours/capacity and sessions where needed.
- [ ] Store historical order item names/options/prices as snapshots; store payment status separately from order status. Never persist card number, CVV or raw payment credentials. Use server-side parameterized queries and environment configuration; never commit secrets.
- [ ] Include reproducible migration, seed, schema, SQL view/report, ERD, documentation, setup, environment, backup/export and restore/recreation files in the repository. Seed all provided products/categories using the correct names and existing image paths; do not invent definitive menu values. Make seed operations repeatable. Mark sample reviews/orders as demo and exclude demo sales from real analytics.

## Catalog, filters and best sellers
- [ ] Store and retrieve categories/products through backend APIs. Preserve All, Sandwiches, Bakery, Drinks, Desserts and the existing mapped subcategories; category tiles apply filters and navigate to Menu. Full Menu opens with the selected category when applicable.
- [ ] Allow only authorized owner/admin users to add, edit, safely delete/deactivate, enable/disable, change category, description, price, image, availability and featured status. Product changes appear without code edits.
- [ ] Calculate best sellers from actual eligible order-item quantities. Exclude cancelled and demo/test sales, document the eligible sales definition, and show featured fallback clearly as fallback rather than fabricated sales.

## Cart, checkout, orders and payments
- [ ] Keep cart add/remove/quantity controls, item prices, subtotal, delivery fee, total, continue-shopping and clear-cart behavior. The cart may be a browser convenience; it is never authoritative for prices, availability or order persistence.
- [ ] Support Delivery and Pickup. Collect full name, phone, optional/necessary email, delivery address only for Delivery, order notes and payment method; validate before submit. Do not create an order by opening/viewing a cart or clearing it.
- [ ] On checkout confirmation, validate product IDs, availability and quantities on the server; compute prices, options, discounts, fees, subtotal and total server-side; transactionally create the order, order items, snapshots, payment/status records and initial event; rollback on critical failure; return an order reference. Handle idempotent retries and do not report success if persistence failed.
- [ ] Persist order lifecycle and history. Support Pending, Confirmed, Preparing, Ready for Pickup, Out for Delivery, Delivered, Completed, Cancelled, with order-type-appropriate transitions. Admin status changes are authorized and durable. Keep completed/cancelled orders for history, analytics and reporting.
- [ ] Support Cash on Delivery and Cash on Pickup without claiming that online payment occurred. Do not enable card/wallet payments as live transactions until a real gateway, credentials and webhook verification are configured. Store payment status separately; never store raw payment credentials.
- [ ] Public order tracking uses an unguessable capability or authenticated ownership, reveals only necessary tracking information, and reflects persisted status changes—not elapsed-time simulations. Protect full order/customer details.

## Reservations, reviews and notifications
- [ ] Reservation form collects customer name, phone, email, guests, date/time and special requests; validates inputs, creates a database reservation/reference and returns confirmation. Persist owner-visible reservation data. Owner can confirm, reject, cancel or complete reservations. Availability conflicts are prevented transactionally; operating hours, slot duration and capacity are configurable. Keep seeded defaults editable and document their assumptions.
- [ ] Reviews are validated and persisted. Store sample reviews as database seeds, not permanent frontend content. Use moderation status; only approved reviews are public and contribute to average rating/count. Owner can review/approve/reject pending submissions when moderation is enabled.
- [ ] Generate durable, deduplicated in-app notifications for actual order placement and persisted status transitions. Link to customer/order, allow authenticated customers to view and mark read/unread; provide safe guest order notifications via tracking capability if guests have no account. Do not claim email/SMS/push without a configured and tested provider.

## Authentication, owner dashboard and analytics
- [ ] Implement secure login/session handling, password hashing if custom authentication is used, customer/admin roles, protected dashboard routes and backend authorization. Admin access is not enforced only by hidden frontend controls. Provide a one-time secure initial owner setup; never hardcode credentials.
- [ ] Owner dashboard provides protected order list/detail/search/status/date/type filters and status updates; product/category management; reservation list/search/filter/detail/status changes; review moderation; and analytics based on actual database rows.
- [ ] Analytics include order counts by status, revenue by selected period with explicit payment/status/demo eligibility, most-ordered products, product sales by category, upcoming reservations, average approved customer rating and review count. SQL examples include product/category joins, customer order counts with threshold, products never ordered, date-range totals, date/day/week/month aggregation and reservations per day.

## API, quality and delivery
- [ ] Implement modular API/routes/services, validation, safe errors, proper HTTP codes, rate limiting where appropriate, protected endpoints and no unnecessary exposure of customer data or secrets. Preserve existing frontend response contracts where possible and connect all existing functional UI to the APIs.
- [ ] Document all tables/relationships, APIs, migrations, seed assumptions, environment variables, local run instructions, database initialization, backup/restore and external provider requirements. Clearly distinguish complete features, features awaiting external configuration, and unimplemented limitations.
- [ ] Verify migrations, seed idempotency, relationships, constraints, views/report queries, transactions/rollback, API validation, access-control boundaries, catalog updates, server totals/price snapshots, order lifecycle, reservation conflicts, reviews/moderation, notifications, analytics and frontend regression. Commit logical changes only to `feature/backend-database-integration`; do not modify or merge into `main`.
